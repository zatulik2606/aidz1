# ADR 0002: Обработка изображений в Telegram-боте через OpenRouter

- Статус: принято
- Дата: 2026-05-17

## Контекст

Проект развивается из базового текстового ассистента в ИИ-продукт роли старшего инженера мониторинга ИТ-сети.  
По `vision.md` бот должен:

- принимать аварийные события в Telegram, включая фото;
- анализировать изображение и выдавать рекомендации;
- оставаться простым (KISS) и расширяемым;
- использовать OpenRouter как провайдер по умолчанию;
- иметь отдельный клиент обработки изображений как точку расширения.

OpenRouter поддерживает image input в `chat/completions` через `image_url`:

- по URL;
- по `data:image/...;base64,...`.

Также OpenRouter рекомендует порядок контента в сообщении: сначала текст, затем изображение.

## Рассмотренные подходы

1. **Передавать в OpenRouter URL файла Telegram**
   - Плюсы: без base64-кодирования, меньше CPU в приложении.
   - Минусы: URL содержит bot token, ограничен по времени, риски утечки и нестабильности.

2. **Скачивать фото из Telegram и отправлять base64 в OpenRouter (in-memory)**
   - Плюсы: без внешнего хранилища, без публичных ссылок, предсказуемо и просто для MVP.
   - Минусы: больше размер запроса и расход памяти/CPU на кодирование.

3. **Сохранять фото во внешнее хранилище (S3/Cloud) и отправлять публичный/подписанный URL**
   - Плюсы: экономия трафика между ботом и LLM, удобно для повторного использования.
   - Минусы: дополнительная инфраструктура, сложность, лишнее для текущего этапа.

## Решение

Принят подход **№2**: скачивать фото через Telegram API и отправлять его в OpenRouter как `base64` (`image_url` data URL), без сохранения на диск.

Технические правила:

- В `handlers.py` использовать `message.photo[-1]` (максимальное доступное качество).
- Скачивать файл в память и передавать в `image_client.py`.
- В `image_client.py` формировать мультимодальный запрос:
  - сначала текстовая инструкция;
  - затем изображение (`image_url` с base64).
- Использовать отдельные переменные:
  - `LLM_IMAGE_MODEL`
  - `SYSTEM_PROMPT_IMAGE`
- Ошибки image-анализа обрабатывать как и текстовый сценарий: fallback пользователю + технический лог.

## Почему это решение

- Соответствует KISS: без новой инфраструктуры.
- Безопаснее URL-подхода: не отправляем временные Telegram-ссылки с токеном.
- Полностью соответствует целям `vision.md` (отдельный image-клиент, расширяемость).
- Достаточно для текущего MVP и легко расширяется в будущем.

## Последствия

Положительные:

- Стабильная обработка фото без зависимости от публичной доступности файлов.
- Простая архитектура с отдельным `image_client.py`.
- Единый паттерн взаимодействия с OpenRouter.

Негативные/ограничения:

- Рост размера payload для больших изображений.
- Дополнительная нагрузка на кодирование base64.
- При высоком трафике может потребоваться переход к внешнему хранилищу (подход №3).

## План эволюции

Если объем фото-запросов вырастет, перейти на гибрид:

- по умолчанию base64 для простых/закрытых случаев;
- URL из объектного хранилища для крупных и частых медиа.
