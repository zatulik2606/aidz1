# ADR 0003: Обработка голосовых сообщений через OpenRouter `input_audio`

- Статус: принято
- Дата: 2026-05-17

## Контекст

Проект — Telegram-бот роли старшего инженера мониторинга ИТ-сети.  
По `vision.md` требуется обработка аудио в сценарии `chat-audio`:

- пользователь отправляет голосовое сообщение;
- бот выполняет транскрипцию/интерпретацию;
- возвращает структурированные рекомендации по инциденту.

Ограничения проекта:

- KISS, без лишней инфраструктуры;
- OpenRouter — провайдер по умолчанию;
- отдельный аудио-клиент как точка расширения;
- минимальная задержка между сообщением пользователя и ответом.

## Рассмотренные подходы

1. **Нативное аудио в chat-completions через OpenRouter (`input_audio` base64)**
   - Модель получает сразу текстовую инструкцию + аудиоданные в одном запросе.
   - OpenRouter документированно поддерживает `input_audio` (base64 + `format`).

2. **Двухшаговый пайплайн с Whisper API**
   - Шаг 1: отдельная транскрипция аудио (Whisper).
   - Шаг 2: передача текста в модель анализа инцидента.

## Решение

Принят подход **№1**: использовать нативное аудио OpenRouter через `input_audio` (base64) в `chat/completions`, без Whisper на текущем этапе.

## Почему это решение

- Соответствует `vision.md` (явно зафиксировано: audio через OpenRouter, без Whisper).
- KISS: один клиент, один запрос, меньше интеграций и точек отказа.
- Быстрее разработка и сопровождение (нет отдельного STT-сервиса).
- Лучше контроль контекста: инструкция и аудио обрабатываются моделью совместно.

## Последствия

Положительные:

- Простая архитектура аудио-сценария.
- Меньше сетевых вызовов и меньше glue-кода.
- Единый OpenAI-compatible стек для text/image/audio.

Негативные/ограничения:

- Нужен корректный формат аудио (`ogg`, `wav`, `mp3`, и т.д.) для выбранной модели.
- Размер payload растет из-за base64.
- Качество распознавания зависит от конкретной выбранной модели OpenRouter.

## Правила реализации в проекте

- Добавить `src/audio_client.py` как отдельный модуль (точка расширения).
- В `handlers.py` для voice:
  - скачать файл из Telegram;
  - передать байты + формат в `audio_client`.
- В `audio_client.py` формировать запрос:
  - `content[0]`: текстовая инструкция анализа;
  - `content[1]`: `{ "type": "input_audio", "input_audio": {"data": "<base64>", "format": "<fmt>"} }`.
- Использовать отдельные env-переменные:
  - `LLM_AUDIO_MODEL`
  - `SYSTEM_PROMPT_AUDIO`

## Когда пересматривать решение

Пересмотреть в пользу отдельного STT (Whisper или аналога), если:

- требуется детерминированная транскрипция как отдельный артефакт;
- появятся строгие SLA/требования к WER по конкретным языкам/шумным каналам;
- потребуется независимая постобработка текста до LLM-анализа.
